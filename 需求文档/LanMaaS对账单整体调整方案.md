# LanMaaS 对账单整体调整方案

## 文档信息

| 项目 | 内容 |
| --- | --- |
| 文档版本 | V1.6 |
| 编制日期 | 2026-09-13 |
| 需求来源 | `需求文档/Lanmaas对账单.doc` |
| 实施原则 | 原有统计逻辑不变；消费日志保留为事实数据；新增独立日汇总表；新增代码与原模块隔离 |

## 1 方案结论

新增独立的管理员对账模块。现有 `logs` 消费日志仍是事实数据源；新增按天汇总表和归档状态表，由主节点在后台逐日生成。查询自动合并“已归档日汇总”和“当天及尚未归档的原始日志”，完成日月聚合、分页与 XLSX 导出。

本次只新增：

1. `GET /api/reconciliation/bills`
2. `GET /api/reconciliation/options/users`
3. `GET /api/reconciliation/options/models`
4. `GET /api/reconciliation/export`
5. 独立的管理员对账页面与菜单入口
6. `reconciliation_daily_summaries` 日汇总表
7. `reconciliation_archive_states` 连续归档状态表
8. 仅主节点执行的逐日归档与历史回填任务

用户和模型筛选均从现有消费日志中读取去重候选项，不依赖当前用户表、模型元数据或模型名称匹配规则。

本次明确不做：

- 不使用 `quota_data` 作为对账数据源。
- 不删除或改写原始 `logs` 数据。
- 不修改 `/api/log/stat`、`/api/data` 及其现有行为。
- 不修改 `SumUsedQuota` 和 `quota_data` 缓存调用链。
- 不修改现有统计页面、统计组件及其请求逻辑。

## 2 约束与落地方式

| 约束 | 落地方式 |
| --- | --- |
| 原表结构不变 | 不修改 `logs`、`quota_data` 等原表；只新增对账专用表，并通过 `AutoMigrate` 自动创建。 |
| 原有统计逻辑不变 | 新增功能通过独立文件实现，不修改现有统计控制器和模型方法。 |
| 只使用现有数据 | 汇总数据只由 `LOG_DB` 中现有 `logs` 消费日志生成，不引入新的计费口径。 |
| 接口可以增加 | 新增账单、日志用户选项、日志模型选项与导出四个 GET 接口。 |
| UI 风格保持原样 | 分别复用 `web/default` 与 `web/classic` 当前布局、组件、主题和响应式规则，不切换站点主题。 |
| 时间与时区口径 | 沿用现有统计和部署环境的时间处理约定，不为对账模块新增独立时区参数或转换规则。 |
| 三库兼容 | 日期分组表达式集中封装，并分别适配 SQLite、MySQL、PostgreSQL。 |

## 3 现状判断

| 现有能力 | 可复用内容 | 本需求缺口 |
| --- | --- | --- |
| 消费日志 | `Log` 已包含 `user_id`、`username`、`created_at`、`model_name`、`quota`，消费类型为 2。 | 现有日志接口返回逐条记录，不能按用户、模型和日月聚合。 |
| 数据看板汇总 | `quota_data` 已按小时缓存部分消费数据。 | 受开关和异步刷新影响，不适合作为对账数据源，本次不调整其实现。 |
| 管理权限 | 已有 `middleware.AdminAuth` 和前端管理员路由守卫。 | 尚无独立对账菜单、页面、聚合接口和导出接口。 |
| 筛选数据 | 消费日志已保存 `user_id`、`username` 与实际 `model_name`。 | 需要增加只读去重查询，避免当前用户或模型配置与历史账务数据不一致。 |
| 列表能力 | 已有 `SectionPageLayout`、`DataTablePage`、分页、空状态和加载状态。 | 需要对账专用筛选栏、只读列和导出动作。 |
| 费用显示 | 已有 `QuotaPerUnit` 和账单货币格式化函数。 | 页面与导出需要使用同一配置快照。 |

## 4 目标调用结构

```text
管理员对账页面
  ├─ 调用 /api/reconciliation/options/users 获取日志用户筛选项
  ├─ 调用 /api/reconciliation/options/models 获取日志模型筛选项
  ├─ 调用 /api/reconciliation/bills 查询账单
  └─ 调用 /api/reconciliation/export 导出账单

新增 reconciliation controller
  └─ 新增 reconciliation service
       ├─ 新增 reconciliation model 合并日汇总与未归档 logs
       ├─ 主节点后台任务逐日生成日汇总并回填历史
       └─ 新增 reconciliation export 生成 XLSX
```

新增控制器只负责参数解析、权限后的调用和响应。统计口径放在新增 service，数据库差异、分组和计数放在新增 model。列表与导出共用同一个 `ReconciliationFilter`。

禁止修改：

- `controller/log.go` 中的原有统计接口。
- `controller/usedata.go` 中的数据看板接口。
- `model/log.go` 中的原有统计方法。
- `model/usedata.go` 中的缓存与汇总流程。

## 5 后端调整

### 5.1 文件规划

| 位置 | 调整内容 |

| `dto/reconciliation.go` | 定义筛选、选项、聚合行和响应 DTO，不直接暴露 `model.Log`。 |
| `service/reconciliation.go` | 负责日期边界、筛选选项、统计口径、费用换算以及列表与导出的复用逻辑。 |
| `model/reconciliation.go` | 只实现 `logs` 的选项查询、聚合、分组计数和三库日期表达式。 |
| `model/reconciliation_archive.go` | 定义日汇总/归档状态，按自然日幂等重建汇总并原子推进连续完成区间。 |

除路由注册和侧边栏入口外，代码尽量通过新增文件实现，避免把对账逻辑放进现有统计文件。

### 5.2 数据查询口径

1. 将 `start_date` 的零点转换为开始时间戳。
2. 将 `end_date` 次日零点转换为排他结束时间戳。
3. `logs` 固定为事实数据源；已完成归档的连续自然日读取日汇总表，其他区间读取 `logs`。
4. 固定限制 `type = LogTypeConsume`。
5. 用户与模型条件使用精确匹配。
6. 日汇总固定按 `user_id`、`model_name` 和自然日分组；月查询在日汇总之上再次按月累加。
7. 使用 `SUM(quota)` 得到聚合额度。
8. 使用相同条件的分组子查询计算 `total`。
9. 列表查询应用稳定排序、`LIMIT` 和 `OFFSET`。
10. service 将 `quota` 换算为 `amount_usd`；查询过程不回写数据。
11. 汇总区间与原始日志区间互斥，最外层再次按维度合并，防止回填期间重复或遗漏。

查询只在以下场景执行：

- 打开对账页面。
- 翻页或改变每页条数。
- 改变日期、用户、模型或统计粒度。
- 导出当前筛选结果。

### 5.3 归档与历史回填

1. 表由 GORM `AutoMigrate` 在升级启动时自动创建，无需手工执行 SQL。
2. 归档任务只在主节点启动，避免主从节点重复执行。
3. 只归档已经完整结束的自然日；每日零点后预留 10 分钟，再归档前一天。
4. 首次上线优先归档最近完整日，使常用的近 7/30 天查询尽快受益；随后每次处理一天、间隔一分钟并向历史逐日回填，避免持续占满数据库。
5. MySQL/PostgreSQL 每个自然日采用事务执行“重新聚合、替换该日汇总、推进状态”。SQLite 在事务外分批读取日志，再以短事务原子替换汇总并推进状态，避免先占用写锁再做长时间聚合；发布时比较状态版本 `revision`，有其他任务先发布则拒绝过期结果并交由任务重试。失败不推进状态；同一天可安全重试。
6. 状态只记录一个连续完成区间。查询将该区间交给汇总表，区间之前、之后（含当天）交给 `logs`，因此回填过程中也可正常查询。
7. 原始日志不删除。若需要核验或重建，可对指定日重新生成汇总。
8. 日汇总只复用 `LogTypeConsume`、`quota`、用户和模型等既有数据，不改变计费和原统计逻辑。

### 5.4 用户名处理

身份分组始终使用 `user_id`。`username` 使用消费日志中的账号快照，避免用户删除后失去可核对信息，也避免 `LOG_DB` 与主数据库分离时跨库连接。

用户筛选下拉按消费日志中的 `user_id` 去重，展示日志中的非空账号快照。即使当前账号已删除或改名，仍以日志身份与快照完成历史对账。

不带账号关键词时优先复用日汇总；输入账号关键词时查询保留的原始消费日志，确保同一用户的历史名称不会因日汇总只保留一个名称而无法搜索。关键词检索仍可能扫描较多日志，不等同于金额查询的汇总加速。

模型筛选下拉按消费日志中的实际 `model_name` 去重，不读取模型元数据的名称规则。输入只用于模糊搜索候选项，点选后使用实际完整模型名精确筛选账单。

### 5.5 退款口径

本期已确认只汇总 `LogTypeConsume`，不纳入退款抵扣，与现有用量统计口径保持一致。

如果后续业务需要改为净额，需要重新确认：

- 是否将 `LogTypeRefund` 作为负数纳入。
- 退款归属退款发生日还是原消费日。
- 跨日和跨月退款如何展示。

即使纳入退款，也可以使用现有日志完成，不需要修改数据库结构。

### 5.6 数据库兼容

日期分组统一由 Go 按服务端本地时区计算自然日/月边界和标签，SQL 使用通用 `CASE WHEN 时间戳 < 周期结束时间 THEN 日期标签 END`，不再依赖数据库会话时区或数据库日期格式化函数。原始日志和日汇总共用相同规则；夏令时通过自然日边界处理，不把一天固定为 86400 秒。

日期边界取该自然日的第一个有效时刻；遇到午夜不存在或重复的时区规则，查询、归档、前后日推进使用同一套边界算法，避免跳入前一天或在同一天循环。

MySQL 新汇总表显式使用 `ROW_FORMAT=DYNAMIC`，不依赖实例默认行格式；已有 COMPACT/REDUNDANT 汇总表先转换再升级索引。用户名与模型名字段分别继承 `logs` 对应字段的字符集和排序规则，保持模型大小写分组及账号比较口径一致。PostgreSQL 汇总的这两个字段使用 `text`，已有受限长度字段通过自动迁移扩容，不截断日志中的模型名称。上述升级只操作新增汇总表，不修改 `logs`。

归档表、状态表和查询逻辑同时兼容 SQLite、MySQL 5.7.8+、PostgreSQL 9.6+；其他新增代码使用 GORM 参数绑定和通用查询构造。所有应用主从节点需使用相同业务时区（例如 `TZ=Asia/Shanghai`），数据库可以使用 UTC。

上线初期保留 366 个自然日的查询范围和 100000 行的导出上限。列表与导出的临时超时均为 300 秒，用于历史回填尚未覆盖时兜底；回填完成并观察生产耗时后可再收紧。

列表使用同一条 SQL 返回全部筛选结果合计、聚合行数及当前页明细，使同一次响应保持一致的读取快照；空页仍返回合计。查询不依赖窗口函数或 CTE，兼容 MySQL 5.7。

### 5.7 导出实现

- 列表和导出共用过滤条件与聚合逻辑。
- 导出不分页，按批次读取或流式写入。
- 固定列为“用户、时间、模型、费用”。
- 费用写入数值，应用千分位和两位小数格式。
- 币种符号使用当前系统账单货币配置。
- 空结果不生成文件，返回固定提示。
- 文件名为 `对账单_YYYY-MM-DD.xlsx`。
- 设置最大导出行数、请求超时和临时资源释放。

### 6.2 界面组合

- 在 default 与 classic 中分别复用各自现有的间距、圆角、边框、主题和响应式规则。
- 顶部筛选栏横向排列，窄屏自动换行。
- 时间预设复用现有按钮组；自定义日期输入保持当前始终可见的交互，不新增展开/收起状态。
- 用户与模型复用现有可搜索下拉模式，并在滚动到底部时继续加载日志候选项。
- 用户列展示头像和账号；头像颜色按用户名稳定生成，复用各主题现有用户头像色规则，保证同一用户在列表、筛选和图表中的颜色语义一致。
- 表格复用 `DataTablePage`、加载骨架、空状态和分页组件。
- 费用列使用现有账单货币格式化函数，不回退为 token 展示。
- 表格上方显示当前全部筛选结果的费用合计，不受分页影响，并复用费用列的货币格式化规则。
- 筛选条件变化时先清空合计金额，成功收到新结果后再显示；查询失败保留空白，查询成功但无数据时显示零。仅翻页或调整每页条数时保留当前合计金额。
- default 对账查询关闭窗口重新聚焦和网络恢复触发的隐式刷新，避免明细自动更新而筛选合计仍保留旧值；打开页面、筛选和翻页仍正常获取新结果。
- 不复制需求原型的品牌、颜色和布局细节。

### 6.3 页面状态

1. 路由搜索参数作为筛选和分页状态源。
2. 默认近 30 天、全部用户、全部模型、按天、每页 20 条。
3. 查询缓存键包含日期、用户、模型、粒度、页码和页大小。
4. 任一有效筛选变化后将页码重置为 1。
5. 日期范围完整并通过校验后才发送请求；日期输入保持始终可见。
6. 用户与模型输入采用防抖搜索，点选候选项后才提交正式筛选。
7. 导出使用当前有效筛选，不携带分页参数。

## 7 实施步骤

| 阶段 | 工作内容 | 完成标准 |
| --- | --- | --- |
| 一 契约与口径 | 时区使用应用部署时区；只统计消费；日期范围最多 366 天；导出最多 100000 行。 | 接口契约可以直接用于联调。 |

| 七 历史回填 | 主节点从最近完整日开始，逐日向历史回填。 | 状态区间连续推进，失败可重试，查询无重复和遗漏。 |

## 8 测试方案

### 8.1 后端测试

- 日期缺失、格式非法、开始晚于结束、结束日全天、跨月和跨年。
- 同一用户多模型、多用户同模型、日月切换、空用户名和空模型名。
- 日期、用户、模型任意组合后的 `total`、分页边界和稳定排序。
- 消费日志用户与模型去重、模糊搜索、分页及非消费日志排除。
- 已删除用户、已下线模型和规则匹配模型仍返回日志中的实际候选值。
- 未登录、普通用户、管理员和根用户权限。
- 文件头、文件名、列顺序、数值格式、全量行数和空数据导出。
- SQLite、MySQL、PostgreSQL 使用同一固定日志数据集执行断言。
- 验证同一天重复归档不会叠加；失败时状态不推进。
- 验证归档区间与未归档日志合并后没有重复或遗漏，月粒度可跨两类数据正确累加。
- 回归验证 `/api/log/stat` 与 `/api/data` 的请求和响应未变化。

### 8.2 前端测试

- 默认筛选条件和每页条数正确。
- 日期范围不完整或顺序错误时不发送请求；自定义日期输入保持始终可见。
- 用户和模型在点选候选项后才更新正式筛选。
- 用户与模型候选项来自消费日志，模糊搜索后提交实际完整值。
- 用户与模型候选项超过单页数量时可以继续滚动加载，无匹配时显示对应空状态。
- 同一用户在多条账单记录中的头像颜色一致，不同用户可通过头像颜色区分，并与各主题现有用户色规则一致。
- 所有筛选变化后页码重置为 1。
- 加载、后台刷新、空状态、错误状态和移动端卡片可用。
- 深色主题与现有页面风格一致。
- 运行 Bun 格式化、lint、TypeScript 检查和生产构建。

## 10 风险与处理

| 事项 | 影响 | 处理方式 |
| --- | --- | --- |
| 消费日志开关 | `LogConsumeEnabled` 关闭期间没有完整对账日志。 | 上线前确认生产环境开启并评估历史缺口。 |
| 日志清理 | 被删除的历史日志无法还原。 | 对账保留期与日志清理策略保持一致。 |
| 退款口径 | 本期只统计消费，可能与财务净扣款不同。 | 已确认本期不纳入退款；如需净额，作为后续独立需求确认跨周期归属。 |
| 时区不一致 | 可能造成日月边界偏移。 | 沿用现有统计与部署时区约定，不增加对账专用时区逻辑；上线检查应用与数据库时区配置。 |
| 历史回填期 | 尚未归档区间仍需扫描原始日志，查询可能较慢。 | 优先最近完整日、逐日回填；临时保留 300 秒超时并监控进度。 |
| 汇总漂移 | 归档完成后若人工补写了带历史时间戳的日志，既有汇总不会自动感知。 | 原始日志永久保留，可按日幂等重建；常规实时日志因 `created_at` 落在当天不受影响。 |
| 账号改名 | 历史账号快照可能与当前名称不同。 | 以 `user_id` 分组，页面展示账务快照。 |
| 货币配置变化 | 不同请求可能展示不同金额。 | 每次请求固定读取一次配置快照并在请求内复用。 |

## 11 发布与回滚

发布顺序：

1. 升级应用，由主节点自动创建对账专用表。
2. 上线四个新增后端接口并启动后台逐日归档。
3. 验证接口权限、归档前后统计结果和性能。
4. 增加前端菜单和页面。

回滚应用时可保留两张新增表，不影响旧版本运行；如需清理，应在确认不再回滚/重建后由运维单独执行。原始日志与原有统计模块无需回滚。
